Clean-Room Glossary & Object Map

A plain-language entry point for engineers reading the sealed ENTITY Protocol 1.0 external conformance kit for the first time. Each term below starts with what the term is in Protocol 1.0 and then, where useful, states a boundary.

Important boundary: this page is non-normative orientation material. The signed conformance kit, its schemas, interoperability profile, canonicalization rules, vectors and pass criteria remain authoritative. The sealed v1.0.2 kit is unchanged.

Core vocabulary

Vector

A vector is a conformance input supplied by the sealed kit and evaluated by a candidate implementation. The black-box interface invokes the candidate with verify --kind <KIND> --input <PATH>; the candidate returns an accepted decision and supporting result data. Required valid vectors must be accepted and required invalid or tampered vectors must be rejected.

Entity

An Entity is a protocol identity identified by an ent1-… or ent2-… identifier and described by a signed sovereign-entity-manifest-v2. The manifest records the Entity ID, Entity classification, display name, aliases, verification methods, active signing key, recovery/cryptographic metadata, creation time, revision and signature.

Entity root

The Entity root is the Entity identity that the Protocol 1.0 interoperability profile treats as authoritative for that Entity. Verification starts from the signed Entity manifest and its active verification method. For ent2, the identifier is opaque and is intended to persist across operational-key or provider replacement.

Sovereign Entity manifest

A sovereign Entity manifest is the signed root identity document whose schema identifier is sovereign-entity-manifest-v2. It is the protocol object a verifier uses to obtain the Entity ID, key material/state, aliases, recovery information and manifest revision before applying identity/signature rules.

Alias

An alias is an alternate string stored in the Entity manifest's aliases array and associated with that Entity. It is an alternate identifier/name for the Entity; Protocol 1.0 does not treat the alias itself as the authority root.

Authority

Authority is permission recognized by Protocol 1.0 for a specific action, relationship or scope after the applicable signed records satisfy the interoperability profile. Authority is evaluated from protocol records and their state, such as signed Entity manifests, scoped relationship evidence, principal bindings, node authorizations and revocations.

In the principal-binding profile, for example, the required relationships include Principal → Installation SOVEREIGN_AUTHORITY, Application → Installation PROCESSING_AUTHORITY, and Device → Installation POSSESSION. These relationships are scoped and revocable.

Sovereign authority

Sovereign authority is authority rooted in the Entity identity/control relationship recognized by Protocol 1.0. In the public principal-binding rules, SOVEREIGN_AUTHORITY is the required active Principal → Installation relationship, verified together with the relevant signed manifests, binding hash, signature and relationship identifiers.

Signature validity

Signature validity means the signature for the applicable protocol object verifies according to the kit's canonicalization and Ed25519 rules using the referenced active verification method and required signature suite. For an Entity manifest, a valid signature establishes cryptographic control by the applicable active verification method.

Legal ownership and objective external-world truth are not protocol-validity states defined by Protocol 1.0. The interoperability profile therefore says that a valid manifest signature, by itself, does not establish those separate external claims.

Schema validity

Schema validity means the JSON object satisfies the structural constraints of its applicable public JSON Schema: required fields, types, constants, enumerations, formats and other schema rules.

Protocol validity

Protocol validity means an input satisfies every Protocol 1.0 rule applicable to that object and operation, not merely its JSON Schema. Depending on the object, those rules include canonicalization/hash checks, signature verification, active verification-method state, authority/binding relationships, revocation state, lineage commitments, version rules and the semantic requirements in the interoperability profile.

A schema-valid object can therefore be protocol-invalid. The sealed kit deliberately includes invalid vectors that are structurally plausible but must still be rejected.

Fail closed

Fail closed means the verifier rejects when a required authority, signature, binding, revocation/version or other mandatory protocol check cannot be established. Unknown major versions and failed required checks are not silently accepted.

Terms that are outside the Protocol 1.0 data model

The interoperability profile occasionally names concepts such as hosting, DNS possession, storage possession, infrastructure ownership, legal ownership or external-world truth to define a boundary. These are not additional Protocol 1.0 object types that an implementer must model for phase-one conformance. Their purpose in the profile is to make clear that those external conditions cannot substitute for the signed/scoped protocol records required to establish authority or validity.

Four implementation distinctions

  1. Entity root vs. alias: verification authority starts from the Entity root; an alias is an alternate manifest value.
  2. Schema validity vs. protocol validity: structural JSON validity is necessary but not sufficient.
  3. Signature validity vs. other external claims: a valid protocol signature establishes the cryptographic fact defined by the profile; it does not automatically establish unrelated claims outside that profile.
  4. Registration/lineage vs. rights/economic conclusions: an asset registration or lineage record proves only the protocol facts it actually contains and verifies.
