Clean-Room Glossary & Object Map

A plain-language entry point for engineers reading the sealed ENTITY Protocol 1.0 external conformance kit for the first time. This page explains vocabulary and object purpose without changing the frozen kit.

Important boundary: this page is non-normative orientation material. The signed conformance kit, its schemas, interoperability profile, canonicalization rules, vectors and pass criteria remain authoritative. The sealed v1.0.2 kit was deliberately left unchanged.

Core vocabulary

Vector

A conformance test case/input supplied by the kit. Here, “vector” does not mean a mathematical vector or an attack vector. Valid and invalid vectors test whether an implementation reaches the expected protocol decision.

Entity / Entity root

A protocol identity represented by an ent1-… or ent2-… identifier and a sovereign Entity manifest. The public interoperability profile treats the Entity root as authoritative. An ent2 identifier is opaque and is intended to persist across operational-key or provider replacement.

Alias

A governed alternate name or identifier associated with an Entity. An alias is not an independent authority source. The clean-room challenge explicitly requires implementations to distinguish aliases from authority.

Authority

Permission recognized by the protocol for a bounded action or scope. It is evaluated from the applicable signed, scoped protocol records. Possession, hosting, storage, naming or topology alone does not create authority.

Sovereign authority

The root/control relationship recognized by ENTITY for an Entity. “Sovereign” in this protocol does not mean a government assertion, and it does not make a hosting provider, DNS holder, storage operator or infrastructure owner authoritative merely because it possesses infrastructure.

Signature validity

A valid manifest signature establishes cryptographic control by the applicable active verification method. It does not by itself prove arbitrary legal ownership or objective external-world truth.

Schema validity vs. protocol validity

JSON Schema establishes structural requirements. Protocol validity also depends on cryptographic verification, authority state, revocation, lineage and semantic rules. A schema-valid object may still be protocol-invalid; the sealed kit intentionally includes invalid vectors that exercise this distinction.

Fail closed

If a required authority, signature or binding check fails—or an unsupported major version is encountered—the implementation rejects rather than silently accepting or widening authority.

Four distinctions to keep visible

  1. Identity ≠ alias. The Entity root is authoritative; an alias is not.
  2. Signature ≠ truth. Cryptographic verification is not a universal truth claim.
  3. Possession/hosting ≠ authority. Provider, device, DNS, storage or infrastructure possession does not automatically create sovereign authority.
  4. Registration/lineage ≠ ownership/economic value. Asset registration and derivation history do not automatically establish title, rights or economic value.
