ENTITY lineage

The code history and the ENTITY history answer different questions.

Git answers

Which commit introduced the change? Who authored or committed it? What are its parents? Which branches, merges and forks preserve that history?

ENTITY adds

Which governed identity and organization are associated with the contribution? What external problem was being addressed? What rights and licence context applied? What evidence validated the work? What later technical, reputational or economic consequence occurred?

Downstream propagation

If a later fork preserves the Git commit history, that repository can retain the same underlying commit ancestry. ENTITY can continue to reference the contribution record and the exact public evidence attached to it.

Why developers should care

A useful contribution can remain attributable beyond the repository where it began.

Ordinary Git history is already powerful. ENTITY is intended to preserve the governed context around that history: identity, authority, provenance, rights, external evidence and consequence. The goal is not to replace Git. It is to make the wider history independently inspectable.

Contribution provenance

Connect public work to a persistent identity and organizational lineage without claiming ownership of upstream code that the licence does not grant.

External validation

Separate internal assertions from reviewer decisions, CI results, merges, rejections and other events controlled by unrelated projects.

Reusable evidence

Carry forward the evidence needed to inspect how a contribution originated and where it later propagated, even as repositories are forked or systems change.

Rights boundary: ENTITY provenance does not convert Vector's MPL-2.0 source into BTG-owned property. It records the contribution and its evidence under the applicable upstream licence and contributor terms. Similar-looking downstream code is not automatically attributed to this contribution without evidence linking the histories.
