Contributor guide · ENTITY v3.4.3

Contribution Workflow

Current runtime: ENTITY v3.4.3. A contribution merged after a release does not silently become part of that release; release qualification and external contribution evidence remain separately versioned.
issue/discussion → bounded proposal → implementation/evidence → pull request → automated checks → review → merge → release qualification where applicable

Good contributions

A reproducible failure, counterexample, unclear specification, portability problem, test improvement or documentation correction is useful. You do not need to understand every subsystem before contributing.

High-impact areas

  • External clean-room implementation and Protocol 1.0 ambiguity reports.
  • Linux/macOS/Windows reproduction.
  • Canonicalization/signature review.
  • Authority/provider-capture counterexamples.
  • BTDU exact reconstruction and scale qualification.
  • Market/recovery/settlement boundary tests.
  • Onboarding, tutorials and documentation usability.

Version discipline

State the exact target you changed or tested: current v3.4.3 runtime, frozen Protocol 1.0, historical v3.4.2 artifact, BTDU 3.4.2 component, or another explicit target. Do not convert a historical result into a current release result merely because code is unchanged.

Claim discipline

Do not label BTG-controlled evidence as independent. Do not upgrade a skipped, inherited or partial result into a fresh PASS. Changes affecting identity, authority, signature meaning, recovery, portability, evidence semantics, rights, settlement or wire compatibility require architecture/governance review and must preserve exact evidence boundaries.

External contribution case studies

Vector and Memnox show how external work can be recorded as attributable contribution lineage after independent upstream review/acceptance. Those case studies are evidence applications of ENTITY, not the definition of the platform, and upstream acceptance does not by itself create payment or ownership rights.
